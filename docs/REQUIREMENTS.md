# 需求原文（用户提供，逐字保留）

请基于 LangChain + LangGraph 构建一个可在本地实际运行的企业客服 Agent 演示系统。请完成实现、测试和浏览器验证，不要只输出架构或伪代码。

## 1. 项目范围与技术方案

* 使用 TypeScript、React Web 界面、Node.js 后端、SQLite、LangChain 和 LangGraph。
* 项目放在 `/workspaces/customer-service-agent/`。默认在主目录 main 分支工作，保留已有改动，不自动创建 worktree。
* 仅本地运行，不部署或发布。微信、飞书暂不接入，通过渠道适配接口预留扩展位置。
* 核对并锁定依赖版本，按照实际安装版本实现，不能混用不同版本 API。
* LangChain 负责动态 Agent、知识检索和工具接入；LangGraph 负责需要明确控制的退款流程及持久化恢复。使用持久化 checkpointer，不能以 MemorySaver 通过重启恢复验收。

## 2. 角色与页面

初始化三个客户“客户甲、客户乙、客户丙”，三个客服席位“A、B、C”，以及独立的“退款审核员”。
提供三个页面：

* 客户端：选择模拟客户身份，发起咨询，连续聊天，查看工单、订单及退款进度，申请转人工。
* 客服工作台：切换客服席位，管理在线状态，查看分配的工单、聊天记录、AI 排查摘要；支持接管、回复、转派和结束服务。
* 审核台：查看退款申请、订单信息、申请理由和相关证据，批准或拒绝并填写意见。

身份切换仅用于本地演示。后端须检查角色、客户归属和工单权限，不能只靠前端限制。
客户端明确标识 AI 回复和人工回复，不展示内部提示词、MCP 参数等实现细节。

## 3. 咨询、分配与会话隔离

客户发送第一条有效消息后，由后端创建咨询工单和会话，再分配客服席位。
A/B/C 默认在线，按轮询分配，跳过离线或达到接待上限的席位；全部不可用时进入等待队列。后续消息保持原分配，新问题可以显式新建工单。
每张工单使用独立的 Agent thread_id，保存客户、工单、客服席位、渠道会话和 thread_id 的映射。不能按客服席位共用上下文，也不能通过切换 thread_id 绕过权限检查。
人工接管后暂停 AI 自动回复，并阻止接管前尚未发送的 AI 回复继续发送；客服可以显式恢复 AI。
会话接待状态、工单状态和退款状态分别保存。

## 4. 知识库与 MCP

准备至少 10 条产品使用、支付异常、退款政策等示例知识。实现检索后回答，展示来源标题和版本；没有依据时说明并追问或转人工。
实现真实 MCP Server，提供订单、支付和退款状态查询工具；用本地 SQLite 初始化至少 6 笔属于不同客户的订单，覆盖未支付、已支付、已退款等情况。
按照当前版本的 LangChain MCP 接入文档连接 MCP Server。Agent 必须实际通过 MCP 查询，不能用普通函数调用冒充 MCP。
数据访问层保留替换为业务 API 或多维表格的能力。服务端注入可信客户上下文，MCP 服务再次检查订单归属，模型不能自行选择其他客户身份。

## 5. 退款审批流程

第一阶段只支持整单模拟退款，不连接真实支付平台。
客户提出退款后，AI 查询订单和支付状态，收集理由，调用提交退款申请工具。
后端检查订单归属、支付状态、可退金额及重复申请。金额使用最小货币单位整数。保存客户、工单、订单、金额、理由、申请版本，生成退款申请编号。
将客户对话与退款审批设计为独立的持久化执行流程：对话使用工单对应的 thread_id，退款流程使用退款申请对应的独立 thread_id。客户等待审核期间仍能聊天和查询进度。
退款流程包括：校验申请、登记审批、等待人工、校验决定、执行模拟退款、记录结果、通知客户。
使用 LangGraph 的 interrupt 与恢复机制等待审核。审核接口先校验身份并保存决定，再向正确流程提交恢复事件。执行节点必须重新读取权威审批记录，不能仅凭恢复参数中的 approved=true 执行退款。
创建申请、发送通知等副作用须与等待节点合理分离并实现幂等；恢复可能重执行节点中的部分逻辑，不能假设从任意代码行继续。
审核批准后，由确定性节点重新核对订单并更新为“已退款（模拟）”；提交成功后再通知客户。拒绝时保存意见，不执行退款。失败时保留失败原因并支持受控重试。

## 6. 状态与执行边界

Agent 可以决定如何追问、检索和查询，但不能自行审批退款、修改审批人或绕过退款资格校验。
工单、审批、订单和执行日志保存为业务数据；Graph checkpoint 保存执行状态，不能代替业务权限和事务控制。
提交申请和执行退款使用稳定幂等键、唯一约束及状态转换检查。发送结果通过持久化发送队列处理，通知重试不能触发再次退款。
同一客户会话有序处理，不同会话可并行；审批回调、客服接管和模型回复之间需要处理并发冲突。

## 7. 验收

至少验证：

* 三个客户发起咨询后分配到 A/B/C，历史与订单互相隔离。
* 重复消息不重复建单；离线、满员和排队规则有效。
* 知识回答有来源；未知政策不编造。
* 查询经过真实 MCP，越权访问被拒绝。
* 未审批和被拒绝的申请不能退款；批准后只执行一次。
* 等待审核期间，对话仍可继续，客户能够查询进度。
* 审核等待期间重启，能够恢复正确的退款流程。
* 审批后执行前、执行后通知前分别重启，结果仍正确。
* 重复回调、并发审批、节点恢复不会重复退款。
* 人工接管后 AI 不抢答；刷新页面恢复真实记录。

## 8. 交付

提供源码、数据库迁移、幂等初始化脚本、示例知识、环境变量模板、本地启动说明、浏览器演示步骤，以及对话与退款流程的状态说明。
支持可配置的真实模型；没有凭据时提供明确标识的 Mock 模式，分别报告 Mock 验证和真实模型验证结果。
实际验证客户、客服、审核三个页面。最终说明已验证能力、未验证外部依赖，以及企业试点仍需补齐的能力。
